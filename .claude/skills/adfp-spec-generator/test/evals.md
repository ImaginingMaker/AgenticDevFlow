# adfp-spec-generator - 评估用例

## 核心场景

| # | 场景 | 预期行为 | 验证方式 |
|---|------|---------|---------|
| 1 | **完整 SPEC 生成** — 提供一份含功能清单、用户故事、验收标准的完整 PRD，要求生成技术规格 | 读取 PRD → 功能模块映射 → 页面架构（页面→区块映射，不展开叶子组件）→ 数据模型 → API 契约 → 状态管理策略（分层策略，不列具体变量）→ 路由设计 → 风险与缓解，输出完整 SPEC 文档 | 验证输出 `spec.md` 含全部 8 个章节，front-matter（phase: SPEC, status: completed, qualityGate: pass） |
| 2 | **页面架构止于区块** — PRD 含「用户列表」页面 | 页面架构输出为页面→区块映射（如 UserListPage → Header, SearchBar, UserTable, Pagination, Footer），不展开叶子组件（如 SearchBar 内部的 Input、Button） | 验证区块列表不包含叶子级组件（如 Input、Button、Icon），下游标注「归 adfp-component-designer 展开」 |
| 3 | **状态管理只定义分层策略** — PRD 含多页面状态需求 | 状态管理策略仅定义数据分层（全局共享 / 页面级 / 组件级 / 服务端缓存），每层说明管理策略和原则，不列具体状态变量名和初始值 | 验证输出含 4 层分层策略表，不含 `const [searchText, setSearchText] = useState('')` 等具体变量定义 |
| 4 | **不规划文件目录结构** — SPEC 包含完整功能模块 | SPEC 输出不包含 `src/components/ui/Button/` 等文件路径规划，功能模块映射表仅映射到页面路径 | 验证 SPEC 中没有文件目录树或「建议目录结构」章节 |
| 5 | **API 契约标注使用页面** — PRD 含「用户管理」功能的多个 API | 每个 API 接口必须标注哪些页面使用该接口，使用「使用页面」列 | 验证 API 契约表含「使用页面」列，每个接口至少标注一个页面 |
| 6 | **数据模型定义** — PRD 含用户、订单等实体 | 数据模型使用 TypeScript interface 定义核心实体，含必填/可选字段；枚举类型使用 type 定义 | 验证数据模型含 interface（字段含 ? 表示可选）和 type 枚举定义 |
| 7 | **路由设计完整** — PRD 含 5 个以上页面 | 路由设计表含路径、页面组件、权限（公开/登录用户/特定角色）、懒加载标记 | 验证路由表格式为 4 列，含懒加载列（✅/❌） |
| 8 | **PRD 格式校验** — 提供功能清单缺失的不完整 PRD | 校验失败，提示「PRD 缺少必需项：功能清单，请补充后再生成 SPEC」；暂停生成不输出任何内容 | 验证不生成 spec.md，仅输出错误提示 |
| 9 | **PRD 格式校验 — 推荐项缺失** — PRD 缺少交互流程和技术约束 | 校验通过（非必须项缺失不阻塞生成），在 SPEC 中标注「待确认」 | 验证 SPEC 成功生成，缺失信息处标注「待确认」 |

## 边界测试

| # | 边界情况 | 预期处理 |
|---|---------|---------|
| 1 | 提供不完整 PRD（缺少功能清单 + 用户故事两个必须项） | 校验失败，提示「PRD 缺少必需项：功能清单、用户故事」，列出全部缺失项，暂停生成 |
| 2 | PRD 中某项功能的技术实现有多个不确定性 | 在对应模块的 SPEC 章节中标注「待确认」并说明可选项（如「状态管理方案可选择 Zustand 或 Redux，需确认」） |
| 3 | PRD 交互流程描述模糊 | 数据模型和 API 契约基于有限信息推导，标注「基于模糊输入推导，建议确认后调整」 |
| 4 | PRD 中未提及任何数据实体 | 数据模型章节输出空，标注「PRD 未定义数据实体，需补充」 |
| 5 | PRD 页面数量为 1（单页应用） | 正常生成，路由设计仅 1 条，状态管理策略简化（页面级 ≈ 全局级），标注「单页应用，分层策略可适当简化」 |
| 6 | PRD 中 API 数量超过 30 个 | 按功能模块分组输出 API 契约表，每组独立表头，标注「大规模 API 清单，建议按模块拆分实施」 |
| 7 | PRD 未定义非功能性需求和技术约束 | SPEC 的风险与技术债章节标注「PRD 未提供技术约束，无法评估技术风险，需补充」 |
| 8 | PRD 中页面名称与区块名称界限不清晰 | 在页面架构中明确定义层级，对模糊页面标注「此页面语义接近区块，需确认是否独立为页面或归入上层页面」 |

## 集成测试

| # | 上下游技能 | 集成点 | 预期 |
|---|----------|--------|------|
| 1 | **上游：adfp-prd-generator** → 本技能 | `prd.md` 的功能清单、用户故事、验收标准、交互流程作为本技能输入 | 本技能进行 PRD 格式校验（功能清单必须、用户故事必须），通过后基于功能清单做模块映射，基于交互流程做页面架构 |
| 2 | **下游：adfp-architecture-designer** | 本技能输出的 `spec.md`（页面架构、数据模型、路由设计）作为 architecture-designer 新项目模式的输入 | architecture-designer 读取 SPEC 的页面架构和路由设计生成文件层级蓝图，基于数据模型推导模块边界 |
| 3 | **下游：adfp-component-designer** | 本技能输出的页面→区块映射（不展开叶子组件）作为 component-designer 工程模式的输入 | component-designer 在 SPEC 的页面→区块映射基础上展开详细组件树（含叶子组件），数据模型用于 Props 接口定义 |
| 4 | **下游：adfp-component-designer**（状态策略） | 本技能输出的状态管理分层策略（不列具体变量）作为 component-designer 输入 | component-designer 基于分层策略设计具体状态变量（如 `searchText`、`userList`），并标注所属层级 |
| 5 | **下游：adfp-architecture-designer**（职责隔离） | 本技能不做文件目录结构规划，architecture-designer 也不做页面→区块映射 | 验证 SPEC 不含「文件结构」或「目录树」章节；architecture-designer 不重新定义页面→区块映射 |
| 6 | **编排：adfo-harness-runner** | 工程模式下，SPEC 阶段完成时更新 harness-runner 的 state.json | 输出路径为 `docs/workflows/{任务ID}/spec.md`，state.json 记录 phase: SPEC, status: completed |
