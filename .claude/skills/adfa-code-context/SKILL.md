# 代码上下文理解

## 核心能力

给定一个文件或文件夹路径，从主入口开始，追踪所有引用（导入、依赖、调用链），
映射完整的逻辑流程，并以简洁的方式呈现，让读者知道"在哪里修改、修改会影响什么"。

## 使用场景

- **项目上手**：刚接触新项目，需要快速理解核心模块
- **Bug 调查前**：先理解调用链，再定位问题
- **代码审查前**：建立心智模型，提高审查效率
- **学习开源功能**：理解开源库的实现机制
- **重构前评估**：评估改动影响范围
- **技术设计评审**：理解当前状态，为设计做准备

## 不适用场景

- 单文件、无外部导入的自包含代码
- 已熟悉模块，只需查看单个函数

## 工作流程

### Step 1: 确定入口点

- **给定文件路径**：直接使用该文件
- **给定文件夹路径**：自动检测主入口，优先级：
  1. `index.ts` / `index.tsx` / `index.js`
  2. `main.ts` / `main.tsx` / `App.tsx`
  3. `package.json` → `main` 字段指向的文件
  4. 文件夹中唯一的顶层文件

### Step 2: 读取主文件，提取关键信息

从主文件中提取：

- **公共接口**：导出的函数、类、组件、常量
- **核心逻辑**：主要业务处理流程
- **依赖项**：所有 import/require 的模块（区分内部与外部）

使用语义搜索（索引项目）、文件读取（大文件）、精确符号查找（特定标识符）。

### Step 3: 追踪内部引用链

对 Step 2 中识别的每个**内部模块**（相对路径导入），递归读取并提取：

- 模块用途（做什么）
- 关键公共接口
- 是否有进一步引用

默认深度限制：默认2层，最大3层。如果某层引用过多，只列出关键路径。

### Step 4: 映射逻辑流程

将 Step 2-3 整合为文本流程图：

```
入口文件
  └─ 调用 moduleA（用途：xxx）
       ├─ 调用 util/helper（用途：xxx）
       └─ 调用 service/api（用途：xxx）
            └─ 依赖 config/constants（用途：xxx）
```

### Step 5: 输出分析报告

遵循下方输出格式。每个模块描述限制在 1-2 句话。聚焦主路径——忽略工具函数、类型定义等次要文件。
阅读后，用户应该知道"在哪里修改、修改会影响什么"。

## 分析维度

| 维度 | 覆盖内容 |
|------|----------|
| **入口用途** | 该文件/模块做什么，解决什么问题 |
| **数据流** | 数据从哪里来，如何处理，到哪里去 |
| **核心调用链** | 最关键的函数/方法调用序列 |
| **外部依赖** | 第三方库及其作用 |
| **副作用** | I/O、网络请求、状态变更、事件监听 |
| **关键配置** | 影响行为的配置项或环境变量 |

### 相关技能

根据分析结果，考虑使用：

- `adfp-architecture-designer` — 全局架构分析
- `adfp-code-reviewer` — 代码质量审查
- `adfa-hooks-extractor` — 提取可复用的 Hooks

### 架构问题反馈通道

当 code-context 分析发现以下架构层面问题时，应在报告中标记并建议触发 `adfp-architecture-designer` 重审：

| 发现 | 触发条件 | 反馈动作 |
|------|---------|---------|
| 循环依赖 | 模块间存在循环 import | 标记 `⚠️ 架构问题：循环依赖`，建议 architecture-designer 重扫依赖拓扑 |
| 全局污染 | 组件使用未隔离的全局样式/变量 | 标记 `⚠️ 架构问题：全局污染`，建议 architecture-designer 更新结构规范 |
| 层级混乱 | 业务模块间互相引用 | 标记 `⚠️ 架构问题：层级混乱`，建议 architecture-designer 重新规划模块边界 |
| 原子化不足 | 组件 >200行 且职责混杂 | 标记 `💡 架构建议：原子化不足`，建议 architecture-designer 更新可复用清单 |
| 规范偏离 | 实际代码与 architecture.md 蓝图不一致 | 标记 `⚠️ 架构漂移`，建议 architecture-designer 同步蓝图 |

报告中以如下格式标注：
```markdown
### 架构问题标记
| 问题 | 严重度 | 建议 |
|------|--------|------|
| {问题描述} | ⚠️ 高 / 💡 建议 | → 触发 `adfp-architecture-designer` 重审 |
```

## 输出原则

- **不重复代码** — 不粘贴大段源码，只提炼关键信息
- **不过度展开** — 外部 npm 包：只说明用途，不深入源码
- **突出主路径** — 工具函数、类型文件、样式：跳过或简要提及
- **流程图优先** — 用树形图表达关系比纯文字更直观
- **保持简洁** — 每个模块描述限制在 1-2 句话

## 执行指令

当用户触发此技能时：

1. **确认目标**：询问或确认用户要分析的文件/文件夹路径
2. **执行分析**：按照上述 5 步工作流程进行分析
3. **生成报告**：使用规定的输出格式生成结构化报告
4. **提供建议**：根据分析结果，给出修改建议和相关技能推荐

如果分析过程中发现代码过于复杂或引用链太深，可以适当简化，
优先保证主路径的清晰度，而非完整覆盖所有边缘情况。

## 职责边界

| 技能 | 边界 |
|------|------|
| adfp-architecture-designer | architecture-designer 扫描**整个项目**识别模块和依赖拓扑（宏观），code-context 追踪**单个文件/模块**内部的调用链和数据流（微观） |
| adfa-hooks-extractor | code-context 理解代码逻辑和数据流，hooks-extractor 专门提取可复用的 Hook 逻辑 |
| adfp-code-reviewer | code-context **建立心智模型**（理解代码在做什么），code-reviewer **评估质量**（检查代码是否做好） |
| adfa-critical-explorer | critical-explorer 审查**设计方案**（编码前），code-context 理解**已有代码**（编码后） |
| adft-page-wiki-generator | page-wiki-generator 生成**页面级**的链路Wiki，code-context 分析**模块级**的代码上下文 |
