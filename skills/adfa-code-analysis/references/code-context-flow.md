# mode:context — 代码上下文分析

**核心功能**：给定文件或文件夹路径，追踪所有引用、映射完整逻辑流程，输出结构化分析报告。

---

## 工作流程

```
确定入口点 → 读取主文件提取关键信息 → 追踪内部引用链 → 映射逻辑流程 → 输出分析报告
```

### Step 1: 确定入口点

| 输入类型 | 行为 |
|---------|------|
| 文件路径 | 直接使用该文件作为入口 |
| 文件夹路径 | 自动检测主入口，按优先级检测 |

**文件夹入口检测优先级**：
1. `index.ts` / `index.tsx` / `index.js`
2. `main.ts` / `main.tsx` / `App.tsx`
3. `package.json` → `main` 字段指向的文件
4. 文件夹中唯一的顶层文件
5. 按字母序的第一个 `.ts`/`.tsx`/`.js` 文件

**检测失败** → 提示用户指定入口文件。

### Step 2: 读取主文件，提取关键信息

| 信息类别 | 提取内容 |
|---------|---------|
| **公共接口** | 导出的函数、类、组件、常量 |
| **核心逻辑** | 主要业务处理流程 |
| **依赖项** | 所有 import/require 的模块（内部 vs 外部） |

**依赖分类**：

| 分类 | 判定标准 | 处理方式 |
|------|---------|---------|
| 内部模块 | 相对路径导入（`./`, `../`） | 递归追踪 |
| 项目模块 | 项目内部绝对导入（`@/`, `~/`） | 递归追踪 |
| 外部包 | npm 包名 | 只说明用途，不深入源码 |
| 类型导入 | `import type` | 只列出，不追踪 |

### Step 3: 追踪内部引用链

| 维度 | 默认值 | 可配置范围 |
|------|--------|-----------|
| 追踪深度 | 2 层 | 1-3 层 |
| 每层最多展开模块数 | 5 个 | 3-10 个 |

**剪枝策略**：当某模块依赖过多（>5 个内部模块）时，只追踪关键模块、其余简要列出。

**跳过分析**（只在模块摘要中提及）：
- 类型定义文件（`.d.ts`）
- 配置文件
- 样式文件（`.css`, `.scss`）
- 测试文件（`.test.`, `.spec.`）
- 外部 npm 包

### Step 4: 映射逻辑流程

树形文本流程图：

```
入口文件（用途：xxx）
  └─ 调用 moduleA（用途：xxx）
       ├─ 调用 util/helper（用途：xxx）
       └─ 调用 service/api（用途：xxx）
            └─ 依赖 config/constants（用途：xxx）
```

```markdown

---
```

### 架构问题反馈

分析中发现以下问题时需在报告中标记：

| 发现 | 触发条件 | 反馈动作 |
|------|---------|---------|
| 循环依赖 | 模块间存在循环 import | 标记 `⚠️ 架构问题：循环依赖` |
| 全局污染 | 未隔离的全局样式/变量 | 标记 `⚠️ 架构问题：全局污染` |
| 层级混乱 | 业务模块间互相引用 | 标记 `⚠️ 架构问题：层级混乱` |
| 原子化不足 | 组件 >200行 且职责混杂 | 标记 `💡 架构建议：原子化不足` |
| 规范偏离 | 实际代码与架构蓝图不一致 | 标记 `⚠️ 架构漂移` |

## 输出原则

1. **不重复代码** — 不粘贴大段源码，只提炼关键信息
2. **不过度展开** — 外部 npm 包只说明用途，不深入源码
3. **突出主路径** — 工具函数、类型文件、样式：跳过或简要提及
4. **流程图优先** — 树形图比纯文字更直观
5. **保持简洁** — 每个模块描述限制在 1-2 句话

---

## 执行指令

1. **确认目标**：询问或确认用户要分析的文件/文件夹路径
2. **执行分析**：按照上述 5 步工作流程进行分析
3. **生成报告**：使用规定的输出格式生成结构化报告
4. **提供建议**：根据分析结果给出修改建议和相关技能推荐
