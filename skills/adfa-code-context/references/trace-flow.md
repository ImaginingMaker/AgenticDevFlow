# 代码追踪执行流程

> 供 `adfa-code-context` 使用。详细描述代码上下文分析中的追踪流程。

## 总体执行流

```
确定入口点 → 读取主文件提取关键信息 → 追踪内部引用链 →
映射逻辑流程 → 输出分析报告
```

---

## Step 1：确定入口点

### 路径处理规则

| 输入类型 | 行为 |
|---------|------|
| 文件路径 | 直接使用该文件作为入口 |
| 文件夹路径 | 自动检测主入口，按优先级检测 |

### 文件夹入口检测优先级

1. `index.ts` / `index.tsx` / `index.js`
2. `main.ts` / `main.tsx` / `App.tsx`
3. `package.json` → `main` 字段指向的文件
4. 文件夹中唯一的顶层文件
5. 按字母序的第一个 `.ts`/`.tsx`/`.js` 文件

### 检测失败处理

- 无法确定入口 → 提示用户指定入口文件
- 文件夹为空 → 提示用户文件夹为空

---

## Step 2：读取主文件，提取关键信息

### 提取内容

从主文件中提取以下信息：

| 信息类别 | 提取内容 | 提取方法 |
|---------|---------|---------|
| **公共接口** | 导出的函数、类、组件、常量 | 正则匹配 export |
| **核心逻辑** | 主要业务处理流程 | 语义分析 |
| **依赖项** | 所有 import/require 的模块 | 正则匹配 import |

### 依赖分类

| 分类 | 判定标准 | 处理方式 |
|------|---------|---------|
| 内部模块 | 相对路径导入 (`./`, `../`) | 递归追踪 |
| 项目模块 | 项目内部绝对导入 (`@/`, `~/`) | 递归追踪 |
| 外部包 | npm 包名 | 只说明用途，不深入源码 |
| 类型导入 | `import type` / `import { Type }` | 只列出，不追踪 |

### 读取策略

| 文件大小 | 策略 |
|---------|------|
| ≤ 200 行 | 完整读取 |
| 200-500 行 | 先读开头了解结构，再读关键函数 |
| > 500 行 | 只读 export 和关键函数签名，按需定位 |

---

## Step 3：追踪内部引用链

### 追踪规则

对 Step 2 中识别的每个**内部模块**（相对路径导入），递归读取并提取。

| 维度 | 默认值 | 可配置范围 |
|------|--------|-----------|
| 追踪深度 | 2 层 | 1-3 层 |
| 每层最多展开模块数 | 5 个 | 3-10 个 |

### 模块信息提取

每个被追踪的模块提取：

1. **模块用途**：用 1-2 句话说清楚做什么
2. **关键公共接口**：导出的主要函数/组件
3. **是否有进一步引用**：是否需要继续深入

### 剪枝策略

当某层引用过多时：

```
场景：某模块依赖 20 个内部模块
处理：
1. 只追踪 5 个关键模块（按引用次数、业务相关性排序）
2. 其余模块在「模块摘要」中简要列出
3. 标注「N 个模块未展开，详见 {路径}」
```

### 跳过规则

以下文件跳过详细分析，只在模块摘要中提及：

| 文件类型 | 处理方式 |
|---------|---------|
| 类型定义文件 (`.d.ts`) | 只列类型名 |
| 配置文件 | 只说明配置作用 |
| 样式文件 (`.css`, `.scss`) | 只列引入 |
| 测试文件 (`.test.`, `.spec.`) | 跳过 |
| 外部 npm 包 | 只说明用途 |

---

## Step 4：映射逻辑流程

### 流程图格式

将 Step 2-3 整合为树形文本流程图：

```
入口文件（用途：xxx）
  └─ 调用 moduleA（用途：xxx）
       ├─ 调用 util/helper（用途：xxx）
       └─ 调用 service/api（用途：xxx）
            └─ 依赖 config/constants（用途：xxx）
```

### 流程图规则

- 层级用缩进表示
- 每个节点标注用途
- 主路径放在前面，分支用 `├─`/`└─` 区分
- 避免在流程图中展示内部细节

---

## Step 5：输出分析报告

### 分析维度

| 维度 | 覆盖内容 |
|------|----------|
| **入口用途** | 该文件/模块做什么，解决什么问题 |
| **数据流** | 数据从哪里来，如何处理，到哪里去 |
| **核心调用链** | 最关键的函数/方法调用序列 |
| **外部依赖** | 第三方库及其作用 |
| **副作用** | I/O、网络请求、状态变更、事件监听 |
| **关键配置** | 影响行为的配置项或环境变量 |

### 报告结构

```markdown
## 代码上下文分析报告

### 基本信息
| 项目 | 内容 |
|------|------|
| 目标路径 | `[文件/文件夹路径]` |
| 入口文件 | `[入口文件路径]` |
| 入口用途 | [一句话描述] |

### 核心逻辑链
[文本流程图]

### 模块摘要
| 模块 | 路径 | 用途 | 类型 |
|------|------|------|------|

### 数据流
[输入 → 处理 → 输出]

### 副作用分析
| 副作用类型 | 位置 | 描述 |
|------------|------|------|

### 外部依赖
| 包名 | 版本 | 用途 | 类型 |

### 关键点与注意事项
- [值得注意的设计决策或潜在风险]

### 建议阅读顺序
1. `[文件路径]` — [原因]
2. `[文件路径]` — [原因]
```

### 架构问题反馈

分析中发现以下问题时需在报告中标记：

| 发现 | 触发条件 | 反馈动作 |
|------|---------|---------|
| 循环依赖 | 模块间存在循环 import | 标记 `⚠️ 架构问题：循环依赖` |
| 全局污染 | 未隔离的全局样式/变量 | 标记 `⚠️ 架构问题：全局污染` |
| 层级混乱 | 业务模块间互相引用 | 标记 `⚠️ 架构问题：层级混乱` |
| 原子化不足 | 组件 >200行 且职责混杂 | 标记 `💡 架构建议：原子化不足` |
| 规范偏离 | 实际代码与架构蓝图不一致 | 标记 `⚠️ 架构漂移` |

---

## 输出原则

1. **不重复代码** — 不粘贴大段源码，只提炼关键信息
2. **不过度展开** — 外部 npm 包：只说明用途，不深入源码
3. **突出主路径** — 工具函数、类型文件、样式：跳过或简要提及
4. **流程图优先** — 用树形图表达关系比纯文字更直观
5. **保持简洁** — 每个模块描述限制在 1-2 句话
