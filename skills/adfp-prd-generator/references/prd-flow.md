# PRD 生成 - 分步执行流程

> SKILL.md 入口页中的路由入口。本文档详细描述 PRD 生成的每一步执行流程。

## 总体执行流

```
用户输入 → [Step 0] 输入验证 → [Step 1] 信息收集 → [Step 2] 用户故事 →
[Step 3] 功能清单 → [Step 4] 交互流程 → [Step 5] 验收标准 →
[Step 6] 非功能性需求 → [Step 7] 约束与假设 → [Step 8] 输出 PRD 文档
```

---

## Step 0：输入验证

### 最小输入检查

用户在触发技能时的输入必须至少包含以下之一：
- **功能名称**：明确的功能/产品名称
- **功能描述**：对功能目标、用途的描述

### 验证流程

1. 提取用户输入中的功能名称和功能描述
2. 若两者均缺失 → 使用输入缺失提示模板引导用户补充
3. 若至少有一项 → 进入 Step 1

### 输入缺失提示模板

```
⚠️ 输入信息不足，无法生成 PRD。

请提供以下信息（至少一项）：
1. 功能名称：例如「用户登录」「购物车」「订单管理」
2. 功能描述：例如「支持手机号一键登录」「用户可以批量操作订单」

示例输入：
- "帮我生成一个用户登录功能的 PRD"
- "我需要一个购物车模块的需求文档，用户可以添加商品、修改数量、结算"
```

## Step 1：信息收集

### 询问项清单

按以下顺序确认，用户未提供则主动询问：

```
🎯 目标用户是谁？
   → 最终使用者是谁？有什么特征？

📋 核心场景有哪些？
   → 用户在什么场景下使用？有哪些典型流程？

💡 要解决什么问题？
   → 当前有什么痛点？本功能的价值是什么？

🔗 与现有系统/功能的关系？
   → 是新功能还是改进？依赖哪些已有功能？
```

### 询问策略

- **优先级**：先问目标用户和核心场景，再问其他
- **收敛规则**：每个问题最多追问 1 次，用户不确定则使用合理假设并标注「待确认」

---

## Step 2：用户故事

### 格式标准

```
作为 <角色>，我希望 <功能>，以便 <价值>
```

### 生成规则

1. 从 Step 1 收集的信息中提取角色和场景
2. 每个核心场景生成 1 个用户故事
3. 每个用户故事对应后续功能清单中的至少 1 个功能

### 示例

```
作为 普通用户，我希望 通过手机号一键登录，以便 无需记住密码即可快速访问。
作为 管理员，我希望 查看所有用户登录记录，以便 监控异常登录行为。
```

---

## Step 3：功能清单

### 表格格式

| # | 功能 | 描述 | 优先级 | 依赖 |
|---|------|------|--------|------|
| F1 | {功能名} | {1-2句描述} | P0/P1/P2 | 无/{依赖的功能} |

### 优先级定义

| 优先级 | 含义 |
|--------|------|
| **P0** | 核心功能，MVP 必须实现，缺此功能产品不可用 |
| **P1** | 重要功能，首版应包含，但不阻塞核心流程 |
| **P2** | 增强功能，可延后迭代 |

### 自动优先级规则

| 条件 | 自动优先级 |
|------|-----------|
| 涉及支付/交易 | P0 |
| 涉及用户注册/登录 | P0 |
| 纯展示类 | 默认 P1 |
| 用户无明确 MVP 范围 | 至多 5 个 P0 |

---

## Step 4：交互流程

### 格式要求

使用文本流程图描述核心用户路径：

```
[入口] → [步骤1] → [步骤2] → [分支判断] → [结果A]
                                      → [结果B]
```

### 生成规则

1. 每个 P0 功能必须有一个交互流程
2. 文本流程图优先，必要时补充关键页面/状态说明
3. 不同用户角色的流程分开描述

---

## Step 5：验收标准

### 格式

P0 功能必须有 1-3 条验收标准：

```
Given {前置条件}
When {用户操作}
Then {预期结果}
```

### 示例

```
功能：手机号登录
验收标准：
Given 用户已输入正确的手机号和验证码
When 用户点击"登录"按钮
Then 系统验证通过，跳转至首页

Given 用户输入错误的验证码
When 用户点击"登录"按钮
Then 系统提示"验证码错误，请重新输入"
```

### 覆盖要求

| 功能优先级 | 验收标准要求 |
|-----------|-------------|
| P0 | 每功能 1-3 条，必须覆盖 Happy Path + 至少 1 条异常路径 |
| P1 | 每功能至少 1 条 |
| P2 | 可选 |

---

## Step 6：非功能性需求

按以下维度评估，用户未提供则标注「待确认」：

| 维度 | 默认假设 |
|------|---------|
| 性能要求 | 首屏 < 2s，交互响应 < 200ms |
| 兼容性 | 现代浏览器最后 2 个主版本 |
| 可访问性（a11y） | 至少满足 WCAG 2.1 A 级 |
| 安全要求 | 敏感数据加密，遵循最小权限原则 |

---

## Step 7：约束与假设

| 约束 | 说明 |
|------|------|
| 技术限制 | 从平台感知检测结果或用户指定 |
| 时间限制 | 用户指定或标注「未确定」 |
| 业务约束 | 从需求中提取的业务规则限制 |

### 处理规则

- 确定的约束 → 直接填写
- 不确定的 → 标注「待确认」
- 用户未提及的 → 留空

---

## Step 8：输出 PRD 文档

### 产物位置

| 模式 | 输出路径 |
|------|---------|
| 敏捷模式（直接调用） | `./prd.md` 或用户指定 |
| 工程模式（通过 harness） | `docs/workflows/{任务ID}/prd.md` |

### 文档 front-matter

```markdown
---
phase: PRD
status: completed
qualityGate: pass
---
```

### 工程模式 CLI 集成

```bash
# 执行前：获取编译后的执行上下文
node skills/adfo-harness-runner/scripts/harness-cli.js context {任务ID}

# 执行后：校验产物并更新状态
node skills/adfo-harness-runner/scripts/harness-cli.js verify {任务ID} PRD {产物路径}
```

---

## 约束规则

1. 不确定的信息主动询问，不做假设
2. P0 功能 ≤ 5 个（MVP 聚焦）
3. 验收标准使用 Given-When-Then 格式
4. 用户故事聚焦用户价值，不写实现细节
5. 生成 PRD 后提供下一步建议（如 → adfp-spec-generator）
