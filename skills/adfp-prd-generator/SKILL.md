# PRD 生成器

> 入口页。详细的分步执行流程见 `references/prd-flow.md`。

从用户的功能描述生成结构化产品需求文档。

## 核心流程

```
信息收集 → 用户故事 → 功能清单 → 交互流程 → 验收标准 → 优先级 → 输出PRD
```

---

## 平台感知

> 公共三链路检测机制（链路 A 工程模式 / 链路 B 敏捷主动检测 / 链路 C 用户指定 → 通用降级）在 `adfo-harness-runner/references/platform-detection.md` 中统一管理。

| 检测条件 | 影响 |
|---------|------|
| `React*` / `JSX` / `TSX` | PRD 章节按 React 技术栈术语描述（组件、Hooks 等）|
| `Vue*` / `Nuxt` | PRD 按 Vue 生态术语描述 |
| `微信小程序` / `小程序` | PRD 突出小程序特有约束（包体积、渲染性能）|
| `Taro` / `uni-app` | PRD 强调跨端适配需求 |
| 未知 | 通用前端 PRD 格式 |

> 工程模式下从 `state.json.techStack` 读取已识别的技术栈，避免重复检测。

## 一、输入验证

### 最小输入要求

用户输入必须至少包含以下之一：
- **功能名称**：明确的功能/产品名称
- **功能描述**：对功能目标、用途的描述

### 输入缺失提示模板

当用户输入不满足最小要求时，使用以下模板引导：

```
⚠️ 输入信息不足，无法生成 PRD。

请提供以下信息（至少一项）：
1. 功能名称：例如「用户登录」「购物车」「订单管理」
2. 功能描述：例如「支持手机号一键登录」「用户可以批量操作订单」

示例输入：
- "帮我生成一个用户登录功能的 PRD"
- "我需要一个购物车模块的需求文档，用户可以添加商品、修改数量、结算"
```

---

## 二、信息收集

首先确认以下信息（用户未提供则主动询问）：

```
🎯 目标用户是谁？
📋 核心场景有哪些？
💡 要解决什么问题？
🔗 与现有系统/功能的关系？
```

---

## 三、用户故事

格式：`作为 <角色>，我希望 <功能>，以便 <价值>`

```
示例：
作为 普通用户，我希望 通过手机号一键登录，
以便 无需记住密码即可快速访问。
```

---

## 四、功能清单

| # | 功能 | 描述 | 优先级 | 依赖 |
|---|------|------|--------|------|
| F1 | {功能名} | {1-2句描述} | P0/P1/P2 | 无/{依赖的功能} |

### 优先级定义

| 优先级 | 含义 |
|--------|------|
| **P0** | 核心功能，MVP 必须实现，缺此功能产品不可用 |
| **P1** | 重要功能，首版应包含，但不阻塞核心流程 |
| **P2** | 增强功能，可延后迭代 |

---

## 五、交互流程

用文本流程图描述核心用户路径：

```
[入口] → [步骤1] → [步骤2] → [分支判断] → [结果A]
                                      → [结果B]
```

关键页面/状态说明。

---

## 六、验收标准

每个 P0 功能必须有 1-3 条验收标准：

| 功能 | 验收标准 | 状态 |
|------|----------|------|
| F1 | Given-When-Then 格式 | 待验收 |

格式：
```
Given {前置条件}
When {用户操作}
Then {预期结果}
```

- 兼容性（浏览器、设备、分辨率）
- 可访问性（a11y）
- 安全要求（权限、数据保护）

## 九、输出：PRD 文档

### 产物位置

| 模式 | 输出路径 | 说明 |
|------|---------|------|
| 敏捷模式（直接调用） | `./prd.md` 或用户指定 | 当前工作目录 |
| 工程模式（通过 harness） | `docs/workflows/{任务ID}/prd.md` | 由编排器指定 |

### CLI 集成（工程模式）

```
# 执行前：获取编译后的执行上下文
node skills/adfo-harness-runner/scripts/harness-cli.js context {任务ID}

# 执行后：校验产物并更新状态
node skills/adfo-harness-runner/scripts/harness-cli.js verify {任务ID} PRD {产物路径}
```

### 文档模板

```markdown
---
phase: PRD
status: completed
qualityGate: pass
---

# {产品/功能名称} - 产品需求文档

**版本**: 1.0
**创建日期**: {YYYY-MM-DD}
**作者**: AI 生成

---

## 1. 概述
### 1.1 产品背景
### 1.2 目标用户
### 1.3 核心价值

## 2. 用户故事

## 3. 功能清单

## 4. 核心交互流程

## 5. 验收标准

## 6. 非功能性需求

## 7. 约束与假设

## 8. 附录
### 8.1 术语表
### 8.2 参考资料
```

## 十、约束规则

1. 不确定的信息主动询问，不做假设
2. P0 功能 ≤ 5 个（MVP 聚焦）
3. 验收标准使用 Given-When-Then 格式
4. 用户故事聚焦用户价值，不写实现细节

---

## 工程模式调用（Harness 调度）

当被 `adfo-harness-runner` 调度时，遵循两阶模式（context → execute → verify）：

### 执行前
LLM 已从 `harness-cli context <taskId>` 获取编译上下文，包括：
- **技术栈**：从 `state.json.techStack` 读取的完整技术栈信息
- **产物路径**：`docs/workflows/{taskId}/prd.md`
- **上游产物**：已完成阶段的产物引用（如 requirement-analysis.md）
- **跳过信息**：已跳过阶段的列表及原因

直接按上下文指令执行，**不需要自行读取 state.json**。

### 执行后
运行 `harness-cli verify <taskId> PRD <artifact>` 校验产物：

```bash
node scripts/harness-cli.js verify <taskId> PRD docs/workflows/<taskId>/prd.md
```

LLM 不能跳过此步骤——状态更新由 verify 命令原子写入，包括：
1. 解析 front-matter 的 phase/status/qualityGate
2. 三判定校验：阶段一致性、内容实质性（≥50字符）、qualityGate 值
3. 原子写入 state.json（先写 tmp → mv）
4. 更新 checkpoint（文件 SHA-256 快照）

## 模板注入

> 共享配置（技术栈、目录约定）由 `adfo-harness-runner/templates/custom.md` 统一管理。

`templates/custom.md` — PRD 模板定制：

```markdown
# PRD 自定义模板

## 项目信息
- 产品名称：{填写}
- 技术栈：{填写}
- 目标平台：Web / H5 / 小程序 / 桌面端

## 默认优先级规则
- 涉及支付/交易 → 自动 P0
- 涉及用户注册/登录 → 自动 P0
- 纯展示类 → 默认 P1

## 验收标准风格
- Given-When-Then（推荐）
- 或：检查清单格式

## 额外章节
- {需要添加的自定义章节}
```
