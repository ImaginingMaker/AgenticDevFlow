# adfp-prd-generator - 评估用例

## 核心场景

| # | 场景 | 预期行为 | 验证方式 |
|---|------|---------|---------|
| 1 | **完整 PRD 生成** — 用户提供功能名称和描述「用户登录功能，支持手机号+验证码一键登录」 | 信息收集 → 用户故事 → 功能清单 → 交互流程 → 验收标准 → 非功能性需求 → 约束与假设，输出完整 PRD 文档 | 验证输出 `prd.md` 含全部 7 个章节，front-matter（phase: PRD, status: completed, qualityGate: pass） |
| 2 | **P0 功能数量限制** — 用户描述需要 8 个核心功能 | P0 功能 ≤ 5 个，其余标记为 P1/P2；在优先级划分中说明 MVP 聚焦原则 | 验证 P0 数量 ≤ 5，超出部分标注为 P1/P2 |
| 3 | **用户故事格式** — 生成多个用户故事 | 每个故事严格按「作为 <角色>，我希望 <功能>，以便 <价值>」格式输出，角色明确、价值可衡量 | 验证所有用户故事含完整的「角色 + 功能 + 价值」三段式 |
| 4 | **验收标准格式** — 为 P0 功能生成验收标准 | 每个 P0 功能有 1-3 条验收标准，全部使用 Given-When-Then 格式 | 验证每条验收标准含 Given（前置条件）、When（用户操作）、Then（预期结果）三个段落 |
| 5 | **信息主动收集** — 用户只说「帮我生成一个登录功能的 PRD」 | 主动询问目标用户、核心场景、要解决的问题、与现有系统的关系；收集后生成 PRD | 验证技能在生成前会发送包含 🎯、📋、💡、🔗 的提问序列 |
| 6 | **不确定性不做假设** — 用户未指定目标平台 | 主动询问目标平台（Web / H5 / 小程序 / 桌面端），不做默认假设 | 验证 PRD 不包含未确认的平台信息，或在「约束与假设」中标注「待确认」 |
| 7 | **交互流程输出** — 功能含多分支流程 | 用文本流程图描述核心用户路径：[入口] → [步骤1] → [步骤2] → [分支判断] → [结果A]/[结果B] | 验证交互流程含分支、条件判断，非简单线性步骤列表 |
| 8 | **非功能性需求覆盖** — 支付类功能需求 | 包含全面的非功能性需求：性能要求（首屏加载、响应时间）、兼容性、可访问性、安全要求 | 验证输出 4 项非功能性需求，安全要求中含支付相关合规说明 |

## 边界测试

| # | 边界情况 | 预期处理 |
|---|---------|---------|
| 1 | 用户未提供任何功能名称和描述 | 使用输入缺失提示模板，引导用户提供功能名称或功能描述，给出示例输入 |
| 2 | 用户仅提供功能名称（如「购物车」），无任何描述 | 触发信息收集流程，依次询问目标用户、核心场景、要解决的问题 |
| 3 | 验收标准超过 5 条（针对单个功能） | 收敛为 1-3 条核心验收标准，补充说明「更多验收标准可后续补充」 |
| 4 | 用户故事中角色不明确（如「用户」过于泛化） | 区分角色类型（普通用户/管理员/运营/访客），引导用户明确多个角色 |
| 5 | P0 功能数量恰好 5 个 | 符合约束规则（P0 ≤ 5），正常按 P0 标记 |
| 6 | 用户需求涉及多个不相关模块 | 建议拆分为多个 PRD 分别生成，标注「建议将此需求拆分为多个独立 PRD」 |
| 7 | 用户需求完全依赖外部系统（如第三方登录） | 在「依赖」列和「约束与假设」中明确标注外部系统依赖关系 |
| 8 | 非功能性需求与技术栈绑定时用户未指定技术栈 | 在「约束与假设」段标注「技术栈待确认」，不硬写框架相关的性能指标 |
| 9 | 功能清单中功能数量超过 20 个 | 按优先级分组展示，P0 组详细展开，P1/P2 组以列表形式列出 |
| 10 | 用户提供的描述中存在相互矛盾的需求 | 标注矛盾点，提问用户确认取舍：「您提到的 A 和 B 存在冲突，请问优先保证哪个？」 |

## 集成测试

| # | 上下游技能 | 集成点 | 预期 |
|---|----------|--------|------|
| 1 | **上游：adfp-requirement-analyzer** | requirement-analyzer 输出的结构化需求作为 PRD 的输入（可选） | 若存在需求分析产物，PRD 直接基于已识别的用户故事和功能清单生成，不做重复分析 |
| 2 | **下游：adfp-spec-generator** | 本技能输出的 `prd.md`（功能清单 + 用户故事 + 验收标准 + 交互流程）作为 spec-generator 的输入 | spec-generator 读取 prd.md 的全部 P0/P1 功能清单，基于验收标准推导技术规格；缺失功能清单时 spec-generator 会校验失败 |
| 3 | **下游：adfp-spec-generator**（校验） | spec-generator 生成 SPEC 前校验 PRD 必要信息 | spec-generator 校验本技能输出的 PRD 是否含功能清单（必须）和用户故事（必须），不含则暂停生成 |
| 4 | **编排：adfo-harness-runner** | 工程模式下，PRD 阶段完成时更新 harness-runner 的 state.json | 输出路径为 `docs/workflows/{任务ID}/prd.md`，state.json 记录 phase: PRD, status: completed |
| 5 | **下游：adfp-spec-generator**（推荐项校验） | spec-generator 校验 PRD 的交互流程和技术约束 | 交互流程为推荐项而非必须项，缺失时 spec-generator 标注「待确认」但继续生成 |
