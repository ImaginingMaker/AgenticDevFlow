# adfp-component-designer - 评估用例

## 核心场景

| # | 场景 | 预期行为 | 验证方式 |
|---|------|---------|---------|
| 1 | **敏捷模式设计** — 用户描述「一个带搜索和筛选的用户列表页」，要求设计组件 | 从零开始，理解需求并输出完整设计文档：需求摘要 → 视觉设计方向 → 组件树 → 状态设计 → Props 接口 → 数据依赖 → 边界情况；7 个章节全部完整 | 验证输出 design.md 包含全部 7 个必需章节，含 front-matter（phase: DESIGN, status: completed, qualityGate: pass, createdAt: ISO8601） |
| 2 | **工程模式设计** — 提供 `architecture.md` + `spec.md`，要求为「用户列表页」设计组件 | 读取 spec.md 的页面→区块映射、数据模型、API 契约、状态策略；读取 architecture.md 的可复用模块清单和文件层级蓝图；在已识别框架内展开详细组件树 | 验证组件树叶子组件不在 spec.md 中展开（仅在 component-designer 输出中展开），Props 接口与 spec.md 的数据模型一致，组件路径遵循 architecture.md 的文件层级 |
| 3 | **视觉设计方向必选** — 用户未提及任何美学要求 | 视觉设计方向步骤不可跳过，必须输出完整的🎨美学方向声明（风格名称 + 字体策略 + 色彩策略 + 空间策略 + 记忆点） | 验证 design.md 含「视觉设计方向」章节，含全部 4 个要素（字体、色彩、空间、记忆点） |
| 4 | **美学方向影响组件拆分** — 选择「极简」美学方向 | 组件拆分策略为更少组件、更大粒度，依赖留白空间处理；不拆分过多装饰性组件 | 验证组件数量合理（不过度拆分），每个组件职责明确，无纯装饰性空壳组件 |
| 5 | **美学方向影响组件拆分** — 选择「极繁」美学方向 | 组件拆分策略包含更多装饰组件、层级叠加，空间处理为受控密度、重叠布局 | 验证含装饰性/容器组件（如 DecorativeBackground、LayeredContainer 等），布局含重叠/叠加模式 |
| 6 | **组件树 — 区分组件类型** | 组件树中每个节点标注类型：展示型 / 容器型 / 组合型 | 验证组件树格式为 `ComponentName（类型）`，三种类型均正确标识 |
| 7 | **状态设计 — 最小化原则** | 状态清单中每个状态标注所在组件和来源（内部 useState / API 请求 / 全局 Store）；能被内部处理的状态不提升到父级 | 验证状态表含「所在组件」和「来源」列，无不必要的状态提升 |
| 8 | **Props 接口完整定义** | 每个组件定义 TypeScript interface，含必填/可选标注（?），回调函数以 on 开头 | 验证每个组件均有对应 Props interface，可选字段含 ?，回调命名 on{Action} |
| 9 | **数据依赖完整覆盖** | 包含 4 种场景处理策略：加载中 → Loading/Skeleton、数据为空 → 空状态引导、请求失败 → 错误提示+重试、组件崩溃 → ErrorBoundary | 验证设计文档含 6×4 的数据依赖表（4 种场景 × 处理策略） |

## 边界测试

| # | 边界情况 | 预期处理 |
|---|---------|---------|
| 1 | 敏捷模式用户描述极其模糊（仅一句「帮我设计一下页面」） | 主动提问引导用户提供信息：目标功能、目标用户、关键交互；标注「待澄清」直到获得基本输入 |
| 2 | 工程模式缺少 architecture.md（仅提供 spec.md） | 正常执行。architecture.md 为可选项，缺少时组件路径不限于预定义文件层级，路径标注「待 architecture-designer 规划」 |
| 3 | 工程模式缺少 spec.md（仅提供 architecture.md） | 正常执行但提示「spec.md 缺失，将仅基于 architecture.md 的可复用清单进行组件设计，数据模型和 API 需要补充」 |
| 4 | 需求中存在无法确定的 UX 细节 | 标注「待澄清」并用提问代替假设，不在设计中硬写不确定的方案 |
| 5 | 组件树超过 30 个节点 | 按区域分组输出，先输出顶层容器组件树，再分别展开每个区域的子组件树 |
| 6 | 同一个区块有多种合理组件拆分方案 | 选择一种方案作为主方案，在设计中标注「备选方案」供用户参考 |
| 7 | 无合适的美学方向选择（用户完全无偏好） | 基于功能目的推荐一个合适的方向（如企业工具→工业实用、创意展示→编辑杂志风），并说明推荐理由 |
| 8 | Props 接口超过 8 个必填参数 | 评估是否可将 Props 分组为子对象，或组件职责是否过重需拆分 |

## 集成测试

| # | 上下游技能 | 集成点 | 预期 |
|---|----------|--------|------|
| 1 | **上游：adfp-spec-generator** → 本技能 | `spec.md` 的页面→区块映射（不含叶子组件）、数据模型、API 契约、状态管理策略作为本技能工程模式输入 | 本技能在 spec.md 的页面→区块映射基础上展开详细组件树（含叶子组件），数据模型用于 Props 接口，状态策略用于状态设计 |
| 2 | **上游：adfp-architecture-designer** | `architecture.md` 的可复用模块清单和文件层级蓝图作为本技能工程模式输入 | 可复用模块清单中标记 ✅ 的模块不在本技能中重复设计，直接引用为已有组件；文件路径遵循 architecture.md 的目录约定 |
| 3 | **下游：adfp-code-implementer** → 本技能 | 本技能输出的 `design.md`（组件树 + Props + 状态 + 视觉方向）作为 implementer 工程模式输入 | implementer 按设计文档逐文件实现，Props interface 直接映射为 TypeScript 类型，美学方向用于样式实现 |
| 4 | **下游：adfp-code-implementer** | 本技能和 implementer 共享 `references/aesthetics-guidelines.md` | 本技能输出美学方向声明（方向声明），implementer 根据声明的方向应用 CSS/动画（落地实现） |
| 5 | **编排：adfo-harness-runner** | 工程模式下，DESIGN 阶段完成时更新 harness-runner 的 state.json，输出路径 `docs/workflows/{任务ID}/design.md` | design.md 写入 harness-runner 指定路径，front-matter 含 phase: DESIGN，qualityGate: pass |
